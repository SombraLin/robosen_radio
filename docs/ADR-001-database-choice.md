# ADR-001: 数据库选型决策（SQLite WAL 模式与未来切库触发条件）

## 状态
已接受 (Accepted)

## 背景
RADIO AI 玩偶互动频道平台目前采用微服务/子服务单机部署架构（包含 Backend Service、Crawler Worker、TTS API/Worker 以及 Admin Console 前端）。在代码审查过程中，评估了是否应当将数据层由 SQLite 迁移为外部关系型数据库（如 PostgreSQL / MySQL）。

## 架构决策与第一性原理分析

1. **当前阶段保留 SQLite + WAL + `busy_timeout`**：
   - 系统当前处于单机部署与中小型数据规模阶段（玩偶数量数十个，新闻抓取每日百条级别）。
   - SQLite 启用 WAL (Write-Ahead Logging) 模式后，天然支持"单写多读并发"（读操作不阻塞写，写操作不阻塞读）。
   - 应用层已配置 `PRAGMA busy_timeout=5000`，使并发写竞争时能够排队等待最多 5 秒，彻底移除了应用层粗暴的 Python `RLock()` 串行锁，充分释放了 SQLite 引擎底层的并发性能。
   - 极大地简化了部署运维成本：零外部数据库依赖，启动脚本和容器单机运行极其轻量。

2. **触发 PostgreSQL 迁移的量化条件**：
   未来当系统满足以下**任一**量化条件时，方启动向 PostgreSQL 迁移的方案设计与实施，在此之前不再就数据库选型进行反复争论：
   - **条件一（数据规模）**：`news` 核心业务表历史记录数超过 **50 万行**；
   - **条件二（水平扩展）**：系统架构需要由单机部署演进为**多实例/多机器横向扩展（集群部署）**，需要多机共享集中式数据库实例；
   - **条件三（高并发写）**：设备在线并发心跳与播放日志上报写吞吐超过 **500 QPS** 且出现 SQLite 锁等待超时。

## 影响与结论
- **数据层维护**：统一维护于 `radio-ai-data` 独立模块，连接池设置超时与 WAL 模式。
- **Schema 演进**：通过数据表迁移机制规范演进，人设文案与默认配置抽离为 JSON 种子文件管理。
